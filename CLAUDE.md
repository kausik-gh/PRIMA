## 1. What we are building

**PRIMA** — *Pre-commitment Risk Intelligence for Multi-party Activity.*

A risk layer that runs in **the seconds before a payment is confirmed**, not after. It
scores the sequence, the network and the context around a payment that looks entirely
legitimate on its own, then responds **proportionately** — never with a binary block.

It ships as a **sub-process that plugs into an existing fraud stack** (NPCI-style
real-time scoring, a bank's own rules engine). It is not a replacement for either. Say
this explicitly in every pitch surface.

**Problem statement:** PS3 — *Pre-Commitment Risk Intelligence for Individually
Legitimate Financial Activity*, Fintech & Commerce track, Microsoft Innovation Club,
VIT Chennai.

### The one-sentence version
> Before you press Pay, PRIMA tells you what it knows about who you're paying and what
> just happened on your own account — in one plain sentence you can check — and gives the
> bank a graduated action instead of a freeze.

## 3. Hard constraints — do not violate

1. **No real money. No payment gateway. No Razorpay, no sandbox, no UPI rails.**
   Every rupee in this system is a ledger entry in our own database. The demo is honest
   about this: the UI says "Demo ledger" in the chrome at all times. This was a
   deliberate decision — real-money integration added confusion and zero judge value.
2. **Blocking is never the default action.** The Interrupt Ladder has five tiers; only
   tiers 3 and 4 delay anything, and even then only the specific amount.
3. **Inbound money is never held. Only outbound.** Carry this comment into the code.
4. **Every score ships with a reason.** No endpoint may return a risk number without the
   fired rules that produced it. A score without a reason is a bug, not a shortcut.
5. **ScopedHold holds an amount, never an account.** The rest of the balance stays live.
6. **No ContextFlag trigger phrases in any document, README, or on-screen text.**
   They live in `backend/context/lexicon.py` only. Anything that can be screenshared
   must not double as an evasion script.
7. **No invented statistics anywhere in code comments, UI copy, or docs.** If a number
   is illustrative demo data, label it. See §8.

## 4. Stack (locked)

| Layer | Choice | Why |
|---|---|---|
| API | FastAPI (existing) | Already in repo, WebSocket support |
| Persistence | **SQLite via SQLModel**, file `prima.db` | Audit found zero persistence. SQLite = zero infra, survives restart. `DATABASE_URL` env var allows Postgres later. |
| Realtime | **FastAPI WebSocket with topic channels** | Replaces the dropped Supabase Realtime. Second device for CircuitBreaker just opens a scoped WS. No third-party service. |
| ML | scikit-learn RandomForest (`fraud_model.pkl`) + PyTorch GAT (`gnn_model.pth`) | Both already trained and committed |
| Graph lib (backend) | NetworkX | Existing |
| Console UI | **Vite + React 18 + TypeScript** in `web/` | The existing 6,948-line `frontend/app.js` runs on `DEMO_SIM_MODE = true` and never calls the backend. Grafting onto it costs more than rebuilding. |
| Graph render | `react-force-graph-2d`, with `-3d` behind a toggle | One data shape, both 2D and 3D — directly serves the "2D or 3D graph" requirement |
| Payer UI | Same React app, route `/pay`, mobile-first | Judges scan a QR, no install |
| Styling | Plain CSS with design tokens (`web/src/styles/tokens.css`) | No Tailwind. Tokens are specified in `docs/04-UI-SPEC.md`. |

**Do not add:** Supabase, Razorpay, Redis, Docker, Postgres (for the hackathon build),
Tailwind, a component library, or any auth provider.

```

Phase 2  TrailScore + ContextFlag       → sequence and context scores work
Phase 3  Fusion + Interrupt Ladder      → a decision object exists
Phase 4  ReasonLine (3 renderings)      → decisions are explainable
Phase 5  Payer surface (/pay)           → the beneficiary verdict card
Phase 6  Console surface (graph + log)  → the bank view
Phase 7  ScopedHold + CircuitBreaker    → the two response mechanisms
Phase 8  Operator console + demo acts   → judge-facing scenario control
Phase 9  PatternMemory, AdaptCal, Mesh  → P1 only, if ahead
```

Do not start a phase before the previous one runs end to end. Each phase has an
acceptance check in `docs/05`.

## 8. Honesty rules for content

The earlier planning documents for this project contain claims about RBI's DPIP
timeline, MuleHunter.ai, Supreme Court and High Court rulings, and specific fraud loss
figures. **These have not been re-verified in this build cycle.** Before any of them
appears on a slide or in the UI:

- Verify each against a primary source (RBI annual report, court order, MHA/I4C release).
- If it cannot be verified in time, drop it. Do not soften it into a vague version.
- Never state a number PRIMA "prevents" or "detects" that is not measured by our own
  metrics endpoint on our own demo data.

Demo data is synthetic. Any screen showing it must carry the "Demo ledger" chip.

## 9. What success looks like on stage

The PS names its own success metrics. We report **exactly these**, not precision/recall:

| Metric | Where it comes from |
|---|---|
| Prevented loss value | Sum of `amount` on transactions stopped at tier 3/4 that were ground-truth fraudulent |
| Detection lead time ahead of commitment | `decision.created_at` minus `transaction.attempted_at`, in seconds |
| False-challenge rate on legitimate activity | Tier ≥ 1 decisions on ground-truth-legitimate transactions ÷ all legitimate transactions |
| User comprehension of warnings | Correct answers on the three-option comprehension probe ÷ probes shown |
| Coverage of multi-party structures | Ring/fan structures with ≥1 member scored ≥ tier 2 ÷ all seeded structures |

`GET /api/metrics/ps3` returns these five and nothing else. It is the last screen of the demo.
